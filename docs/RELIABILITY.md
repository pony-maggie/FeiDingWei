# Reliability

## Reliability Goal

FeiDingWei should make agent work visible, reversible, and verifiable. The MVP should prefer explicit draft artifacts and inspectable run history over hidden automation.

## Verification Strategy

Planned verification commands:

```bash
npm run test
npm run build
npm run test:e2e
```

Standard startup and verification:

```bash
./init.sh
```

- Component tests for Inbox unread/read rendering and mark-read calls.

## Agent Safety Rules

- Anonymous users must be redirected to login before accessing app pages.
- Room creation must require an authenticated workspace member.
- New rooms must create the creator as `room_lead`, selected workspace members with their chosen room roles, and default visible Agents.
- Accessible room lists must only include rooms the user can read through workspace admin/owner status or room membership.
- Viewer room members must remain read-only.
- Reviewer room members may send messages, execute review Agents, approve requested reviews, and return drafts for revision.
- Human `@user` mentions must not trigger Agent generation plans.
- Mention notifications must only target mentioned room members and must not notify the sender.
- Notification read-state mutations must only succeed for the notification recipient.
- Agents create drafts by default.
- Mentioned agents show a generation plan preview and require human confirmation before execution.
- Generated tasks and docs can be edited or rejected while still draft.
- Draft tasks and docs can be assigned to humans and sent to a requested reviewer.
- Requested-review approval must reject room reviewers who are not the selected reviewer unless a room lead or workspace admin overrides.
- Return-for-revision must preserve reviewer comments and expose the visible blocked/revision reason.
- People directory must only list members from the current workspace and must not expose users from other workspaces.
- Agents may suggest assignees and review handoffs, but must not approve artifacts or mutate permissions.
- Agent prompts should receive only room-scoped collaboration context, not unrelated workspace data.
- Generated tasks and docs require human approval before becoming active.
- Human decisions are active records; Agent decisions remain draft records and must stay traceable to their source run when generated by an Agent.
- Draft-only mutations must reject stale approve, edit, or reject attempts instead of silently succeeding.
- Agent runs must record status, input, output, error, source message, room, and agent.
- Provider errors must be recorded on failed Agent runs without leaking API keys.
- Failed runs must be visible.
- Tool execution should be sequential in the MVP for easier traceability.

## Observability Expectations

The MVP should expose:

- Agent run status.
- Current LLM provider/model mode.
- Expandable Agent run details with run ID, input, output, and redacted errors.
- Agent output message.
- Agent generation plan preview before execution.
- Generated task and document status.
- Source context from generated artifacts to source messages and agent runs.
- Generated task and document summaries inside agent run history.
- Rejected artifact status so humans can see that a generated draft was reviewed and declined.
- Mention notifications for human `@user` messages so later Inbox views can show collaboration handoffs.
- Inbox unread/read sections and room links for user-scoped collaboration notifications.
- Task/document assignee, owner, reviewer, review status, blocked reason, and reviewer comments.
- People directory member role, function label, team, and active room context.
- Agent run generated-artifact collaboration summaries with assignee/owner, reviewer, and review state.
- Decisions tab entries with creator, status, source message, and source Agent run context.
- Agent run generated-decision summaries.
- Project room JSON export for local backup, debugging, and issue reproduction without exposing provider API keys.

## Clean Restart Expectations

From a clean checkout:

1. Dependencies install.
2. Prisma client generates.
3. Database migrates.
4. Seed data loads.
5. Tests pass.
6. Build passes.
7. E2E workflow passes when the app is implemented.

## Known Reliability Risks

- External model providers can fail or behave differently; v0 uses Pi faux provider for deterministic local runs.
- OpenAI provider mode is optional and requires `FEIDINGWEI_LLM_PROVIDER="openai"` plus `OPENAI_API_KEY`; without a key the app stays on faux provider behavior.
- Agent-generated output can be wrong; human approval remains mandatory.
- Long-running agents can complicate UI state; v0 uses synchronous run completion before introducing streaming.
- Database state can drift; seed and migration commands must remain reliable.
